
## Phase 6: Greedy speculative decoding
Method (ready text): A small draft model (Qwen2.5-0.5B-Instruct, 494 M parameters, same tokenizer as the 1.5B target) proposes k tokens autoregressively using its own KV cache. The fine-tuned target then scores the last accepted token plus the k proposals in a single forward pass, producing its own greedy token at every position. The longest prefix of proposals that equals the target's tokens is accepted; at the first disagreement the target's token replaces the proposal (or, if all k agree, the target's next token is appended as a bonus). Rejected positions are removed from both KV caches by cropping, and the draft cache catches up lazily at the start of the next round. Because every emitted token is the target's argmax given a prefix the target has verified, the output is identical to plain greedy decoding of the target; the draft only changes how many target tokens are obtained per target forward pass.
Facts and numbers: see PROJECT_STATE.md "Key results: P6" (sources spec_bench.csv, spec_env.json, tests/test_spec_equiv.py). Tests 43 passed; real-model equality on real validation prompts (CPU fp32); acceptance 0.65-0.83; pooled speed-up 0.755x (slowdown) on CPU, 2 records, k in {2,4}, warm-up 0, repeats 1.

Discussion points: (1) slowdown is expected here: about 70% of latency is the one-off prompt prefill, which speculation makes 1.25-1.39x longer because the draft must also be prefilled; (2) outputs are 15-16 tokens, so only 4-7 rounds; (3) a verify round cost 3.1-4.1 greedy steps on CPU for 2.1-3.8 tokens (hypothesis, not profiled: compute-bound CPU decoding removes the "extra tokens are free" assumption); (4) only the best cell (k=4, 3.75 tokens/round) reached decode-only break-even 0.99x; (5) a task-tuned draft would raise acceptance (not trained); (6) GPU timing and peak memory were not obtained (quota), computed fp16 weights 3.09 GB + 0.99 GB and KV 28,672 + 12,288 B/token.
