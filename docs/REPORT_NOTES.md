## Phase 5: KV-cached autoregressive decoding (rubric D1-D3)  [append to docs/REPORT_NOTES.md]
FACTS: two own greedy decoders. Reference: each step re-runs the whole sequence (use_cache=False). Cached: one prefill fills a DynamicCache owned by the loop, then one token per step with position_ids = current length, a 2-D attention mask grown by one and an assertion cache_len == prompt + tokens fed. Both use logits_to_keep=1. Batch size 1. HF generate used only as a reference. Part B: single GQA attention layer with a hand-written cache, RoPE offset and bottom-right causal mask equals full recompute (also with the Phase 4 tiled kernel); negative controls break it.
EQUALITY (results/benchmarks/kv_bench.csv, kv_equiv.csv): fine-tuned 1.5B fp16: identical tokens in 9/9 cells (L 128/512/1024, N 16/64/128); base 0.5B fp16: 4/4 combos (64:16..1024:128), 20/20 validation records equal to no-cache and HF generate, max logit difference 0.078-0.109 yet identical tokens, step-0 logits identical; fine-tuned 1.5B fp32: 4/4 combos, max logit difference 5.3e-5..6.3e-4, 20/20 records. No mismatch observed. Unexplained: HF-generate reference differs on ft1.5B fp32 at L>=256 while both own decoders agree (reported as a limitation).
BENCHMARK (T4, fine-tuned 1.5B fp16, warm-up 2, repeats 5, medians): end-to-end speedup 1.4-1.7x (L=128), 3.9-4.7x (512), 5.6-8.2x (1024); cached decode 55-69 ms/token independent of L (~17 tok/s) vs uncached ~83-125 / ~250 / ~470-490 ms/token at L=128/512/1024; prefill identical (~75-90 / 170-250 / 430-457 ms); peak GPU memory above weights 10-17 MB (L=128) up to 93 MB (cached, L=1024) vs 73 MB uncached; measured KV bytes == 28,672 B/token x (L+N-1) exactly (33.0 MB at L=1024, N=128).
FIGURES/TABLES: results/figures/kv_time.png, kv_memory.png; equivalence table (kv_equiv.csv); benchmark table (kv_bench.csv).
EXPLANATIONS: positions (RoPE rotates by absolute position; wrong position changes logits: negative-control test), masking (length-1 query sees all cached keys; multi-token chunk after a prefix needs a bottom-right offset mask), cache growth (linear; GQA 2 KV heads vs 12 query heads -> 6x smaller than MHA), numerical differences (different GEMM shapes in fp16 change accumulation order: logits differ by ~0.1 while argmax stays equal; fp32 shrinks differences by 2-3 orders of magnitude), cost (cached O(T) per token vs full recompute; speedup grows with L). Flat ~57 ms/token far above the bandwidth bound (~10 ms) suggests per-step Python/launch overhead dominates (hypothesis, not profiled). Cached path uses more peak memory than uncached at L>=512 (persistent cache on top of prefill transients; hypothesis).
DIFFICULTIES: transformers 5.22.1 API (crop takes a negative count; no cache_position argument); HF generate's generation_config merge silently ignoring repetition_penalty=1.0 (Qwen ships 1.05); code written without a working torch in the authoring sandbox, validated on Colab (1 test threshold corrected).

## Phase 6: Greedy speculative decoding
Method (ready text): A small draft model (Qwen2.5-0.5B-Instruct, 494 M parameters, same tokenizer as the 1.5B target) proposes k tokens autoregressively using its own KV cache. The fine-tuned target then scores the last accepted token plus the k proposals in a single forward pass, producing its own greedy token at every position. The longest prefix of proposals that equals the target's tokens is accepted; at the first disagreement the target's token replaces the proposal (or, if all k agree, the target's next token is appended as a bonus). Rejected positions are removed from both KV caches by cropping, and the draft cache catches up lazily at the start of the next round. Because every emitted token is the target's argmax given a prefix the target has verified, the output is identical to plain greedy decoding of the target; the draft only changes how many target tokens are obtained per target forward pass.
Facts and numbers: see PROJECT_STATE.md "Key results: P6" (sources spec_bench.csv, spec_env.json, tests/test_spec_equiv.py). Tests 43 passed; real-model equality on real validation prompts (CPU fp32); acceptance 0.65-0.83; pooled speed-up 0.755x (slowdown) on CPU, 2 records, k in {2,4}, warm-up 0, repeats 1.
Table idea: per (record, k): L, N, acceptance rate, rounds, tokens per round, prefill ms, decode ms, total ms greedy vs speculative, speed-up. Figure idea: spec_overview.png (only if `--mode plot` ran) and a schematic of one round (draft k, verify k+1, accept a, correct/bonus, crop).
Discussion points: (1) slowdown is expected here: about 70% of latency is the one-off prompt prefill, which speculation makes 1.25-1.39x longer because the draft must also be prefilled; (2) outputs are 15-16 tokens, so only 4-7 rounds; (3) a verify round cost 3.1-4.1 greedy steps on CPU for 2.1-3.8 tokens (hypothesis, not profiled: compute-bound CPU decoding removes the "extra tokens are free" assumption); (4) only the best cell (k=4, 3.75 tokens/round) reached decode-only break-even 0.99x; (5) a task-tuned draft would raise acceptance (not trained); (6) GPU timing and peak memory were not obtained (quota), computed fp16 weights 3.09 GB + 0.99 GB and KV 28,672 + 12,288 B/token.

Rejected: re-prefilling the draft each round; HF assisted generation as deliverable.
